### O1. The router folds the post-attention norm (B1, the cheap half)

**Direction.** Remove the operator `L{l}.norm2` from every MoE layer (26 of
27) by letting our router normalise its own input and publish the
normalised row for the expert gate-up. Expected gain 26 x 13.6 us = 0.35 ms.

**Core approach.**

- Today: `norm2` (stock `rmsnorm_layer`, one task) reads `x_res [1, 2048]` and
  writes `h`; the router reads `h` and `W_gate`; `w13` reads `h`, `routing`,
  `mask`. After: the router reads `x_res` and `w_norm2_{l}`, computes the norm
  in the reference's order (`numpy_ref.rmsnorm`: FP32 mean of squares,
  `x * rsqrt(var + eps)` rounded to BF16, then the BF16 weight multiply,
  rounded to BF16), writes `h` as a new first output, and takes its logits
  from the normalised values it already holds in registers. `eps` is the
  model's `rms_norm_eps`, 1e-6 (`numpy_ref.rmsnorm`), passed as a float
  bit pattern like `scaling`. `w13` is
  unchanged: it reads `h`, now written by the router.
- Kernel (`moe_router_mi300.cuh`): each lane already holds `HIDDEN / 64 = 32`
  input elements in `hv[]` (FP32). The norm is a wave-level sum of squares
  over the 64 lanes of wave 0 (`wave_sum`), broadcast through LDS to the
  four waves, then each lane rounds its 32 values as the reference does and
  writes them to `h` with 16-byte stores before the dot products. All four
  waves must read the same statistic, so the sum is computed by all four
  waves redundantly (each wave reads the full row: 4 KB per wave, in L2) or
  once and shared through LDS; the redundant read is simpler and free.
- Chain rule: the router now consumes `x_res`, the output of `o_proj`, and
  produces `h`, which `w13` consumes: both boundaries still share a tensor
  (`graph_plan.chain_violations` stays empty).
- Boundary compare: `h` after the norm is boundary B7 in
  `docs/deepseek-v2-lite/08-correctness.md`; `run_fleet.py` dumps a tensor by
  its last writer, so the router becomes that writer and the compare is
  unchanged. The layer-0 dense block keeps its `norm2` (its consumer is the
  stock silu gang kernel).

**Files.** `fleet/tasks/mi300/moe_router_mi300.cuh` (the norm prologue, one
more input and one more output), `fleet/patches/new_tasks.patch`
(`register_moe_router_mi300_task`: pointer count, the emitted call, the
`eps` parameter as a float bit pattern), `fleet/build_graph.py`
(`moe_router_layer` pointer order), `fleet/graph_plan.py` (the MoE layer
under `--fuse-norm2`, default on once validated), `harness/numpy_ref.py`
(`moe_router` takes `x_res` and `w_norm`; `rmsnorm` reused),
`fleet/tasks/kernel_tests_mi300.cu` and `kernel_tests.py` (the suite's router
case gains the norm), `harness/compare.py` if the B7 label changes.

**Checks here.** `test_numpy_ref` for the composed router against the tiny
model's own modules (the norm then the router, bit-compared as today's parts
are); the dry run's operator count 326 to 300 and the chain check; the
suite's dry run; the offline compile; `check_syntax.sh`.

**Time box.** 3 hours. **On the VM.** The router suite (100 trials), then
`L2_it32` with compare, then the 27-layer ids.

### O2. The silu-mul into the expert down projection's prologue (B2)

**Direction.** Remove `L{l}.silu` (41 us, 8 tasks) by computing
`act = silu(gate) * up` inside the w2 gang kernel, the way the runtime's own
dense path does it (`silu_mul_linear_mi300.cuh`: "output = silu(gate) * up @
weight^T"). Expected gain 26 x 41 us = 1.1 ms, the largest certain item.

**Core approach.**

- The layout today: `w13` writes `mid [1, 8, 2 x 1408]` with the gate half in
  columns `[0, 1408)` and the up half in `[1408, 2816)` of each slot's row
  (`silu_mul_task_impl`: `d_mul = input + OUTPUT_SIZE`); `silu` writes
  `act8 [1, 8, 1408]`; `w2` reads `act8[slot]` as the A row of an M = 1 CK
  GEMM (`gang_moe_w2_linear_kernel`, `a_base = input + slot * REDUCTION_SIZE`).
- After: a copy of the w2 kernel under our patch, `gang_moe_w2_silu`, takes
  `mid` as its input. Each tile (one expert, one N tile of 64 columns, 32
  tiles per expert) computes the 1,408 values of its slot's `act` row from
  `mid[slot]` with `fast_silu`, rounds to BF16 as the stock silu does, writes
  them to a private scratch row, and hands that row to the CK pipeline as
  `a_base`. The scratch is a workspace `[8 x 32, 1408]` BF16 (720 KB), one
  row per (slot, tile), reused by every layer since the chain serialises
  the layers; the plan allocates it with `ROW_SLACK` like every activation.
  The redundancy is 32 tiles computing the same row: 32 x 5.6 KB of reads
  from L2 and 1,408 silu evaluations per tile, microseconds in total.
- The memory-model detail that must be right: the tile writes the scratch
  row with vector stores and then reads it back through the CK tile window
  (buffer loads). Within one workgroup on gfx942 the vector L1 is
  write-through, but an earlier task on the same CU may have left a stale
  copy of that scratch row in L1 (the previous iteration). So the prologue
  ends with a workgroup-scope release fence, `__syncthreads()`, and a
  workgroup-scope acquire fence (`__builtin_amdgcn_fence(__ATOMIC_ACQUIRE,
  "workgroup")`, which lowers to `buffer_inv sc0`, the L1 invalidate) before
  the pipeline runs. The offline disassembly shows the `buffer_inv sc0`
  between the stores and the first buffer load.
- The alternative, an epilogue in `w13`: the 16 x 64 output tile holds 64
  columns of one half, so gate and up of the same intermediate index sit in
  different tiles unless `pack_weights` interleaves the W13 rows in 32-row
  groups (gate 32, up 32) and the epilogue exchanges halves through LDS
  (the dense `gang_linear_silu` does this with 128-row groups,
  `pack_weights.SILU_GROUP_ROWS`). It removes the same operator with a
  repack and a changed `mid` layout that the B11 compare would have to
  undo. The prologue variant needs neither, so it goes first.
- The registration trap: `register_gang_moe_w2_linear_mi300_task` takes
  `reduction_size` from the input tensor's last dimension
  (`task_register.cc`, line 1234: `input_ops[0]->output_tensors[0].dim[2]`).
  With `mid [1, 8, 2816]` as the input that would be 2,816. Our registration
  takes K from the weight's last dimension (1,408) and passes the input row
  stride (2,816) as a separate template argument for the prologue.
- The `act8` boundary disappears from the non-debug graph; under `--debug`
  the plan keeps the stock `silu` operator so every boundary stays
  comparable, as it keeps the snapshots.
- Validation: the kernel suite tests our kernels against NumPy in a
  standalone binary and does not instantiate the CK linears, so O2 is
  validated in the graph, by the boundary compare of `out8` (B12) and the
  ids, not by a suite case.

**Files.** a new header `fleet/tasks/mi300/gang_moe_w2_silu_mi300.cuh`
(the copy of the w2 kernel with the prologue; the stock file is left as is),
`new_tasks.patch` (task type, `register_gang_moe_w2_silu_task` copied from
the w2 registration with one more input, the gang type list in
`runtime.cc` and `persistent_kernel.cuh`, a `gang_moe_w2_silu_linear_layer`
in the Python API), `build_graph.py`, `graph_plan.py` (`--fuse-silu`),
the workspace in `make_tensors`.

**Checks here.** the dry run (300 to 274 operators with O1), the chain
check, the wrappers' assertions for the new call, the offline compile with
the `buffer_inv sc0` read from the disassembly, the numpy check unchanged
(the math is the stock silu followed by the stock w2).

**Time box.** 4 hours. **On the VM.** `L2_it32` compare: B12 (`out8`, the
expert outputs) within threshold proves the fusion; then the ids.

### O3. The input norm as a prologue of the per-tile linear (B1, the other half)

**Direction.** Remove `L{l}.norm1` (27 operators) and `head.norm` by
normalising inside the per-tile Q/KV projection and inside `lm_head`.
Expected gain 28 x 13.6 us = 0.38 ms. The runtime's fused kernel is not on
the MI300 path (`02`, "What the double-check changed"), so this is our
registration of a stock kernel with a prologue.

**Core approach.**

- Today `qkva` under `--tile-linears` is the stock `linear_layer`: 96 tasks,
  the weight `[3648, 2048]` partitioned on dim 0 by the grid (each task 38
  rows), the input `[1, 2048]` whole, the output partitioned on dim 1
  (`persistent_kernel.py`, `linear_layer` imaps). `lm_head` is the same
  shape with `[102400, 2048]`.
- After: `linear_norm_mi300`, our task type, registered like
  `register_linear_task` with two more inputs: `w_norm [2048]` and a scratch
  `[G, 2048]` BF16 partitioned on dim 0 by the grid, so the runtime hands
  each task its own scratch row (the per-task pointer rule of
  `fleet/tasks/README.md`). The task normalises the 4 KB input row into its
  scratch row in the reference's order (O1's code, shared in
  `mla_common_mi300.cuh` as `rmsnorm_row`), fences as in O2, and calls
  `linear_kernel_ck` with the scratch row as the input. The 96 tasks each
  redo a 2,048-element norm: 96 x 4 KB of L2 reads, nothing.
- The scratch is partitioned on dim 0 by the grid, and the runtime offsets
  each task's pointer by `dim / grid_dim.x * bid.x` rows, so the row count
  must be a multiple of the grid: one scratch per grid size, `[96, 2048]`
  for the Q/KV projection and `[400, 2048]` for `lm_head`
  (`grid_for_linear(V)`, the `size // 256` branch), 0.4 and 1.6 MB.
- Validation is in the graph, as for O2: the boundary compare of `qkva`
  (B2) and of the logits, then the ids; the suite has no CK linear.
- The chain rule: `qkva` now consumes `x_res` (written by the previous
  layer's combine, or by `embed` for layer 0) and produces `qkva`, consumed
  by `mla_prep`. The compare loses `h` after `norm1` (B1) in the non-debug
  graph; `--debug` keeps the stock norm operator.

**Files.** `fleet/tasks/mi300/linear_norm_mi300.cuh` (the prologue, then
the batch-1 tier of `linear_kernel_ck` copied rather than called: the A
tensor view's coherence bits live inside that function, and the copy gives
the A view the `sc0` bit of O2's pattern; the residual path is left out),
`new_tasks.patch` (the registration: from `register_linear_task`, the two
extra tensors, the emitted call; the layer method lives in `build_graph.py`
as the other new tasks do), `build_graph.py`, `graph_plan.py`
(`--fuse-norm1`), the workspaces. Done 2026-09-17; the fused linear is
per-tile whether or not `--tile-linears` is set, and the scratch is the
task's second output (as O2's), not a third input.

**Checks here.** the dry run (274 to 246 operators), the chain check, the
offline compile (this instantiates the CK linear for gfx942 in the offline
translation unit for the first time, which the day-1 build did on the VM
only; if the offline unit cannot instantiate it, the syntax check and the
VM build carry the item), the numpy check of `rmsnorm` then the linear
against the tiny model.

**Time box.** 5 hours. **On the VM.** `L2_it32` compare (B2 `qkva` within
threshold), the ids, the event clock.

### O4. Per-tile elementwise operators as a fallback (C4)

**Direction.** If O2 slips, spread `silu` over 66 tasks and `combine` over
64 instead of 8 and 8, under `--tile-moe`. Worth up to 1 ms only if the
cost is per task rather than per operator, which the empty-task ladder
(Part 2) will say; the layer table suggests per operator.

**Core approach.** The combine can use the stock registration with a larger
grid: `moe_mul_sum_add_layer` with `grid_dim = (1, 64, 1)` gives each task 32
columns through the imap. The silu cannot: `silu_mul_task_impl` finds the up
half at `input + OUTPUT_SIZE` of the per-task tile, and a tile of the input
row holds gate columns only, so a per-tile silu needs our variant with the
full-row stride as a parameter (`moe_silu_mul_tile_mi300`, 20 lines, the
same registration pattern as `copy`).

**Files.** `graph_plan.py`, `build_graph.py`; for the silu, a small header
and a registration in the patch. **Time box.** 2 hours. Done only if O2 is
not done.

### O5. The residual linears: what the reading found, and the probe (C3)

**Direction.** The residual variants of the stock linear cost 22 us
(`o_proj`, 8 MB) and 34 us (`down`, 46 MB) against 4 us for the plain
15 MB `qkva`. The reading of `linear_ck_mi300.cuh` on 2026-09-17: the
residual is added in the store epilogue only (`residual_add &&
d_residual`, lines 478 to 610); there is no second pass and no workspace.
The kernel does not explain the floor. What does: `o_proj` follows the
merge and `down` follows `gate_up`, both operators of 8 gang tasks spread
over 8 XCDs, while `qkva` follows the one-task `norm1`; the layer table's
pattern (`02`, the last row of the double-check) says a boundary after a
multi-XCD producer costs 13 to 40 us. So C3 is very probably Group A, and
the local deliverable is a probe, not a kernel.

**Core approach.** `graph_plan.py --probe-before L0.o_proj`: insert a
one-task `copy` operator before the named operator: it copies the
producer's output (`attn`, 4 KB) into a twin tensor and the named operator
reads the twin, so the chain rule holds on both sides. On the VM, if `o_proj`'s gap drops from 22 us to
about 4 with the probe in front, the floor is the boundary's spread, not the
kernel, and the remedy is Group A's. The probe is also how the empty-task
ladder's finding is confirmed inside the real graph.

**Files.** `graph_plan.py`, a test. **Time box.** 1 hour, plus the reading
already done.

### O6. Non-temporal loads for our kernels' cache streams (C2)

**Direction.** E2 (`-DMPK_NT_WEIGHT_LOADS`) is worth 2 ms because the
stock linears' weight streams stop evicting what the attention re-reads. Our
kernels stream the latent cache the same way and still use plain loads.
Expected gain 0 to 0.5 ms; two hours to find out.

**Core approach.**

- The stock kernels get the policy through CK's tensor view:
  `amd_buffer_coherence_enum` value 18, which on gfx942 is `sc1 nt` (the
  encoding is shared with gfx950, checked in `fleet/patches/README.md`).
  Our kernels load through `load8` (`mla_common_mi300.cuh`, a `uint4`
  dereference). A second helper `load8_nt` issues the same 16 bytes with
  the policy: `__builtin_amdgcn_raw_buffer_load_b128(rsrc, voffset, 0, 18)`
  with the resource from `__builtin_amdgcn_make_buffer_rsrc(base, 0,
  0xffffffff, flags)`, or inline `global_load_dwordx4 ... sc1 nt`; the
  offline disassembly decides which one the compiler honours (the `nt`
  bit must appear on the load).
- Where it applies: in the VALU attention every cache row is read twice per
  tile, once in the scores pass and once in the p x V pass (the second from
  L2). Streaming loads on the first read could evict the row before the
  second, so the policy goes on the second read only (the row's last use)
  under `-DMLA_NT_STREAMS`; in the MFMA kernel of O7 each row is read once,
  so every cache load streams. The merge's partials loads are read once and
  stream as well. The `ql_nope`, `q_pe` and `W_uv` loads keep the default
  policy (re-read across tiles).
- The stores of the partials could use `__builtin_nontemporal_store` as the
  stock silu does (`nt_store_u64_hip`); the merge reads them back on other
  XCDs through L2 misses anyway, so the store policy is a second, separate
  toggle.

**Files.** `mla_common_mi300.cuh` (`load8_nt`), `mla_attend_mi300.cuh`,
`mla_merge_uv_mi300.cuh`, `run_fleet.py` (`--nt-streams` sets the define
through `MPK_EXTRA_HIPCC_FLAGS`), the kernel suite build flags. **Checks
here.** the offline compile with the `nt` bit read from the disassembly;
the suites unchanged in math. **Time box.** 2 hours.

### O7. The MFMA attention (C1)

**Direction.** Rewrite `mla_attend` so that the score and the p x V
products run on the matrix cores and the cache tile is read once, staged in
LDS. The VALU kernel costs 34 us per tile grid standalone against a 9 us
bandwidth floor; the MFMA version should cost a few microseconds per tile
and be load-bound. Expected gain 27 x (34 - 10) = 0.65 ms once Group A is
solved; it is also the kernel that O7's successor B5 (the last-split
merge with `W_uv` per split) needs.

**Core approach.**

- The instruction: `v_mfma_f32_16x16x16_bf16` (`__builtin_amdgcn_mfma_f32_16x16x16bf16_1k`
  on gfx942; the `16x16x32` form used by `paged_attention_decode_minimal`
  exists only on gfx950, which is why that file is gated in `gfx942.patch`).
  One instruction multiplies a 16 x 16 A by a 16 x 16 B into a 16 x 16 FP32
  C held across the 64 lanes, 4 values per lane. The operand layout the
  design assumed (`docs/mla-decode/04-our-kernel-spec.md`): lane `l` holds
  A[l mod 16][4 (l div 16) .. +4] and B[4 (l div 16) .. +4][l mod 16], and
  D[4 (l div 16) + i][l mod 16] for i in 0..3. This is what the offline
  compile can lower but not verify; the kernel suite on the VM verifies it
  (100 random trials against `numpy_ref.mla_attend`, bit-compared at the
  rounding points the reference fixes).
- Shapes per tile: M = 16 heads, the pass of `TILE` rows as N, K = 576 for
  the scores (36 MFMA steps of 16 over `[ql_nope | q_pe]` against
  `[c_kv | k_pe]`), then p x V with K = the pass rows and N = 512 (32
  column blocks of 16). With `TILE = 16`: one wave computes the whole score
  block (36 instructions, about 300 cycles), the four waves split the 512
  output columns (128 each: 8 column blocks, 1 k-step of 16 rows), and the
  accumulator per wave is 16 x 128 FP32, 32 registers per lane.
- LDS: `ql_nope` and `q_pe` as BF16, 18 KB (the A operands, read per step
  with `ds_read_b64`); the cache tile `[16, 576]` BF16, 18 KB; `k_pe [16, 64]`
  2 KB; the scores `[16, 16]` FP32 1 KB and the BF16 probabilities 0.5 KB;
  the running max, sum and alpha per head. About 40 KB of the 57 available,
  so `TILE = 16` fits and `TILE = 32` (58 KB) does not; the number of passes
  doubles (26 rows per split is two passes), which is fine because the pass
  cost is the load latency, not the compute.
- The loads: the tile's 20 KB is loaded cooperatively (256 threads x 80
  bytes: five 16-byte loads per thread, all issued before the first use, so
  a pass costs about one HBM latency plus the LDS writes) and, to overlap,
  the next pass's loads are issued into registers (20 VGPRs) before this
  pass's MFMAs run. Under `-DMLA_NT_STREAMS` (O6) these loads stream.
- The softmax keeps the reference's rounding points exactly as today:
  scores in FP32, the running max and the rescale in FP32, the
  probabilities rounded to BF16 before p x V (they are the MFMA A operand
  now, which is what the comment in the kernel anticipated), `l` summed
  from the unrounded probabilities, `o = acc / l` and `lse = m + ln(l)` at
  the end. Since the probabilities and the products are already what
  `numpy_ref.mla_attend` computes, the numpy reference does not change;
  only the FP32 summation order inside a 16-wide K step differs, which
  the thresholds absorb (the scores boundary B5 has a 2.6e-3 floor).
- What stays VALU: the score scaling, the max and sum over 16 columns per
  head (one lane per head after a transposition through LDS), and the
  final normalisation.
- Register budget: the accumulator (32), the A fragments in flight (8 to
  16), the prefetch registers (20), addresses and loop state: about 90
  VGPRs in a unified file of 512 per lane on gfx942 where MFMA accumulators
  may be placed in the AGPR half; how the compiler allocates them inside
  the worker's union is read from the offline resource print.
- Unchanged: the tile decode (`split_id = t * 8 + xcd`), the empty-split
  fill (`lse = -inf`), the partials layout `[n_splits, NH, P_ROW]` and the
  split count, so the merge, the registration, the plan and the suite's
  split cases need no change; only the kernel body is new.
- Build flag `-DMLA_ATTEND_MFMA` selects the kernel; the VALU version stays
  as the reference implementation and the fallback. The suite runs both.

**Files.** `fleet/tasks/mi300/mla_attend_mfma_mi300.cuh` (new; the
registration emits the same call, the choice is the define),
`mla_common_mi300.cuh` (the MFMA fragment helpers), the suite's build
(both variants), `run_fleet.py` (`--mfma-attend`). Done 2026-09-17 with
three departures from the sketch above: the 36 score steps are split nine
per wave and reduced through LDS (4 KB) rather than run on one wave; the
V fragment is read from the row-major staged tile as four strided
`ds_read_u16` (no transposed copy, 16 KB of LDS saved); the query and the
tile rows are stored at a stride of 584 elements (16-byte aligned, banks
spread), the `[c_kv | k_pe]` row being one address formula for both
products. LDS 42,176 B.

**Checks here.** the offline compile with the `v_mfma_f32_16x16x16_bf16`
mnemonic counted in the disassembly, no spills, the LDS size under 57 KB
from the resource print; `check_syntax.sh`; a NumPy emulation of the
operand layout in `fleet/tests` (a 16 x 16 x 16 product assembled from the
per-lane fragments the kernel would hold, against the plain product) so the
lane arithmetic is tested before the machine sees it; the suite's dry run.

**Time box.** 1.5 days. **On the VM.** the suites (both splits cases and
the scores case), `KT_TIME` standalone against the VALU 34 us, then the graph.

### O8. The prefetch operator: the runtime patch (D1), only if time remains

**Direction.** Let the idle workers stream the next operator's weights into
the 256 MB memory-side cache while the current operator runs. Expected 0.5
to 0.8 ms; it needs a runtime change because the graph is a chain by
construction.

**Core approach.**

- Where the chain comes from (`runtime.cc`, `register_mugraph`, the loop
  over operators): for each customized operator the runtime takes
  `pre_op`, the previous operator in registration order, asserts that the
  two share a tensor, creates events sized by the gcd of the producer's and
  consumer's partitions (`dfs_create_events_add_tasks`), sets each producer
  task's `trigger_event` and each consumer task's `dependent_event`, then
  makes the current operator `pre_op`. A task has exactly one of each.
- The patch: an operator registered with a marker (a parameter on our
  `prefetch_layer`, or a task type in a set) is treated as a *side*
  operator: its tasks get the dependent event of the operator that follows
  it in registration order (computed by running the pair analysis for
  (`pre_op`, `next_op`) as if the side operator were absent), their
  `trigger_event` is the end-of-graph event with `num_triggers` raised by
  their count, and the side operator does not become `pre_op`. In the
  worker nothing changes: a side task waits like any task, runs, and
  signals an event that only the iteration's end waits on. The end-of-graph
  event is an ordinary counted event, so a prefetch that finishes after
  its consumer only delays the end of the iteration, never the consumer.
- The task (`prefetch_mi300.cuh`): 256 threads walk a `[rows, K]` BF16 slice
  with 16-byte loads and accumulate into one register that is written to a
  dummy output, so the loads cannot be elided; the grid partitions the
  weight on dim 0 so each task takes a stripe; the plan gives the expert
  prefetch the router's event (it reads `mask` to pick the eight experts).
- The interaction with E2: the stock linears' non-temporal loads bypass the
  memory-side cache on allocation (`sc1 nt`, MALL no-allocate). If the
  prefetch allocates the lines and the consuming linear then reads them
  with `nt`, whether the read hits the cache is a question for the machine;
  the experiment runs D1 first without E2 on the consuming linears, then
  with.

**Files.** `new_tasks.patch` (`runtime.cc`: the side-operator branch of the

Done 2026-09-17 with two departures: the side operator is registered right

## Double-check of this page (2026-09-17)

Verified in the source:

- `silu_mul_task_impl` finds the up half at `input + OUTPUT_SIZE`
  (`silu_mul_mi300.cuh`); `gang_moe_w2_linear_kernel` reads one token's
  slot row as an M = 1 CK view (`gang_moe_linear_mi300.cuh`, lines 296 to
  340); the dense fused pattern exists as `silu_mul_linear_mi300.cuh`. O2's
  prologue form follows the runtime's own precedent.
- The residual add of `linear_kernel_ck` is in the store epilogue only
  (`linear_ck_mi300.cuh`, the `residual_add && d_residual` sites); no second
  pass. O5 is a probe for that reason.
- The stock `rmsnorm_linear` and `gang_rmsnorm_linear_mi300.cuh` are not on
  the MI300 include path (`tasks/mi300/task_header.cuh`); O3 is our
  registration.
- The runtime chains operators to their immediate predecessor and gives a
  task one dependent and one trigger event (`runtime.cc`, lines 505 to
  615); O8 needs the side-operator branch.
- The per-tile `linear_layer` partitions the weight on dim 0 and the output
  on dim 1 and leaves the input whole (`persistent_kernel.py`, lines 2058
  to 2060); O3's scratch is partitioned on dim 0 the same way as the weight.
- `MPK_NT_WEIGHT_LOADS` is CK coherence value 18 on the B view of every
  stock linear (five files); our kernels use `load8`, a plain `uint4` load.
- The VALU attention reads each cache row twice per tile (the scores pass
  and the p x V pass); O6 streams the second read only.
- The reference norm order is FP32 statistics, the normalised value rounded
  to BF16, then the BF16 weight multiply (`numpy_ref.rmsnorm`, lines 56 to
  58); O1 and O3 reproduce it.
- `MPK_ENABLE_TIMING` prints for `worker_id < 8` and accumulates per stock
  type (`persistent_kernel.cuh`, lines 995 to 1010 and 1125 to 1160); I1
  extends both.
- The `copy` task exists with one parameter (`new_tasks.patch`,
  `register_copy_mi300_task`); I2 and I3 build on it.
- The generated dispatcher keys on type and variant id together
  (`runtime.cc`, line 1587), which is why the duplicate value 188 (O0)
  went unnoticed in session B.
- The w2 registration reads K from the input tensor (`task_register.cc`,
  line 1234) and the per-task pointer offset is `dim / grid_dim.x * bid.x`
  (`fleet/tasks/README.md`), the two traps written into O2 and O3.
